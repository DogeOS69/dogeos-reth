# Tsuki witness corpus recipe

`generate.sh` starts a node built from this worktree on a short Tsuki chain and drives six blocks
through the Engine API exactly as the rollup node drives a sequencer, so everything it produces
comes from the same `newPayload` path the base-fee rule is enforced on. It then dumps one
`debug_executionWitness` per block, with `provenance.json` and `SHA256SUMS`.

```bash
scripts/tsuki-witness-corpus/generate.sh [OUT_DIR]   # default: target/tsuki-witness-corpus
```

Needs `cast` (foundry), `jq` and `python3`. The node runs in the foreground of the script and is
stopped by its exit trap.

It builds the node under a lock, so it does not start a second heavy cargo job beside one that is
already running. The default lock is repo-local; on a machine shared with other builds, point
`BUILD_LOCK` at whatever lock those builds use:

```bash
BUILD_LOCK=/path/to/shared/build.lock scripts/tsuki-witness-corpus/generate.sh
```

## What it checks

It is this repo's end-to-end check of the node, not only a fixture generator. Against the running
node it asserts that:

- a base fee one wei off the rule is answered `INVALID`, and for the base-fee rule rather than
  for anything else about the payload — the probe's header is re-encoded and re-hashed, after
  first confirming that the encoding reproduces the hash the node itself computed;
- the node still accepts the correct payload afterwards, so a rejection is not a node failure;
- the pending block still builds and `eth_simulateV1` still runs with `validation: false`, which
  is what separates building a block from validating one;
- every witness covers the L2SystemConfig account's path in the state trie, compared node by node
  against the node's own `eth_getProof`, both while slot 101 is unset and after it carries an
  overhead.

## The chain

Chain id `6281971`, borrowed from Chikyū so that a guest has an authenticated L2SystemConfig
address for it — a guest refuses a chain it does not know. **It is not Chikyū.** The corpus runs
its own genesis schedule: Tsuki from genesis, so the fee parameters are (48, 10), where Chikyū's
canonical spec never activates Tsuki and stays on Feynman's (8, 2). The genesis document also
differs in its allocations: three funded development accounts, a gas burner, and the stand-in
overhead setter `SSTORE(101, calldataload(4)); STOP` at the L2SystemConfig address, with slot 101
unset.

Six blocks are driven, and the wrong-fee probe's correct payload becomes a seventh, so the run
produces seven witnesses (`1.json` … `7.json`).

## Relationship to the guest's fixtures

The guest's fixture corpus is **not** generated here. It is generated by a copy of this recipe
that lives with the fixtures, in `stateless-block-verifier` at `testdata/dogeos/base-fee-rule/`,
so the committed recipe is the one that produced the committed fixtures. That copy takes the
genesis document, the port and the way the L2SystemConfig account comes about from the
environment, covers the shapes this one does not (the account absent entirely, created mid-chain,
and the registered development chain), and dumps SBV `BlockWitness` documents rather than raw
`debug_executionWitness` responses.

Keep the two in step: a change to the block sequence or the assertions here belongs there too.
